# A person's own desktop place (container + folder + LAN ports)

Some people get more than a chat: a desktop in the browser on the GPU host, with their own browser, Telegram client and the tools they work with (video editing, their own Steam account). A **place** is one container per person, started on request and stopped when not used, with its own folder. The operator's own place was the first one; `place.py` makes the next ones the same way.

| Piece | What |
|---|---|
| `Dockerfile.place` | the linuxserver webtop (Debian, XFCE, Selkies streaming) plus Brave, the Telegram desktop client and an **all-English environment** (`LANG`, `LC_ALL`, locale generated). Brave launches with `--no-sandbox`: the container runs with `no-new-privileges`, where Chromium's own sandbox cannot start, and the container is the sandbox |
| `place.py` | `create NAME` (folders, a secret kept 0600 and never printed, the container, **not started**), `start`, `stop`, `status`, `creds` (the path, never the password), `rm` (keeps the person's files) |
| `place_selftest.py` | offline checks with a fake docker |

## Status, how to run it, and what the proof of concept showed (2026-11-25)
**What exists and works.** Two places ran side by side on one GPU host (RTX 3060 Ti 8 GB, Ryzen 5 5600X 12 threads, 31 GB), the same image, each with its own folder, docker network, LAN address, limits and gate token: Brave, Telegram, VLC, htop, ffmpeg and DaVinci Resolve free 21.2, streamed to a browser by Selkies with NVENC H.264 1080p60 zero-copy. The bot opens and closes a place (`gateway escritorio`), an idle clock closes it after 30 minutes with a warning, a metrics log records what each session costs, and two places played a LAN game against each other. What is *not* done: Steam and Epic logins (the person does them), the way in from the internet, dynamic game ports, and a fix for the mouse in first-person games (below).

**Run it.**
1. *Images:* `docker build -f Dockerfile.place -t bridgeai-place:latest .` in this folder, then `build-resolve.sh DIR` for the Resolve layer (DIR holds the free `DaVinci_Resolve_*_Linux.zip` and `makeresolvedeb_*_multi.sh`; the vendor's installer download is done by hand: the helper that asks the vendor's site for the link returned 403 on 2026-11-25). Rebuilding the first image rebuilds the second (about 25 minutes); small helper changes need no rebuild because `to-resolve` and `from-resolve` are mounted from this folder.
2. *Host network, once:* install `places-net.sh` as `/usr/local/sbin/places-net.sh` and `bridgeai-places-net.service` in `/etc/systemd/system`, write `/etc/default/bridgeai-places` (`PLACE_IPS=(ADDRESS1 ADDRESS2)` and, for a game, `PLACE_GAME_UDP=(PORT)`), `systemctl enable --now bridgeai-places-net`. Reserve those addresses in the router.
3. *A place:* `sudo place.py create NAME --image bridgeai-place-resolve:latest --gpu --bind ADDRESS [--udp PORT]` (folders, login in `.desktop.env`, gate token in `.gate.token`, container not started), `start|stop|status NAME`, `recreate NAME [--image] [--bind] [--udp PORT|--no-udp]` (keeps folder, ports and login; refused while it runs), `gate-token NAME --rotate`.
4. *The bot:* put `"escritorio": {"host", "token"}` in the person's stack of the master gateways file (the token is read as root from `NAME/.gate.token`) and run `ops/gateways_sync.py`; the gate needs `place_control.py` next to `gate.py` and a restart. The stack gets the verbs with the next image.
5. *Look at it:* `python3 -I gate/places_report.py [--since MINUTES]` reads the gate's `places-metrics.csv` (one row per running place per minute: in use, idle seconds, CPU, memory, outgoing rate, own VRAM, card use, encoder, VRAM, power, temperature, places open, host load) and prints the cost of one session, how the card scales with the number of places open, and how many sessions like those fit, naming the resource that runs out first.

**Measured on that host (two places unless noted).**

| Case | Result |
|---|---|
| Two YouTube streams | GPU 6 %, NVENC 15 %, VRAM 1.2 GB, 59 W, 47 C; each place 26 to 32 % of a core (Brave decodes video on the CPU, the card's decoder was at 0 %), 1.1 to 1.3 GB RAM |
| One place rendering in Resolve (free edition) | the container pinned at its 5-core cap (496 %), the card at 13 to 16 % and 2.1 GB VRAM: DNxHR is encoded on the CPU, the cap is what limits the render |
| Two LAN-game instances (Quake III demo) | GPU 13 to 15 % (NVENC 12 to 14 %), VRAM 1.3 GB, about 25 % of a core and 0.5 GB RAM each, streams of 0.5 and 1.0 Mbit/s, both rendering on the card's own OpenGL |
| NVENC sessions | 12 parallel 1080p30 sessions all ran (the driver's session limit is lifted on this host) |
| Isolation, tested from inside both places | internet and DNS work; the router, the host's GPU gate and Sunshine, the other place and the old docker network were all unreachable |
| Source decode on the card | `to-resolve` decodes H.264 on NVDEC (about four times real time for 1080p60) |
| Report on the first minutes of the log | VRAM 25 sessions, NVENC 9, GPU use 45, CPU 444, RAM 61: the encoder is the first limit at Quake-class cost; a modern game's VRAM (3 to 6 GB) would come first, which this log cannot say until it holds such a session |

**Exporting from the free edition without enormous files.** DNxHR is a fixed bitrate per tier, so the default `hq` is large. Measured on a 10 s 1080p60 clip (synthetic, a busy test pattern; ProRes and the H.26x encoders vary with the picture, DNxHR does not):

| Codec | Size for 10 s | About per hour |
|---|---|---|
| DNxHR HQ | 550 MB | 198 GB |
| DNxHR SQ | 363 MB | 131 GB |
| ProRes 422 HQ | 195 MB | 70 GB |
| ProRes 422 | 145 MB | 52 GB |
| DNxHR LB | 113 MB | 41 GB |
| ProRes 422 LT | 112 MB | 40 GB |
| ProRes 422 Proxy | 55 MB | 20 GB |
| H.265 NVENC (cq 23), a delivery file | 20 MB | 7 GB |
| H.264 NVENC (cq 21), a delivery file | 30 MB | 11 GB |

The way to keep exports small: export from Resolve an *intermediate* that its Deliver page offers (DNxHR LB or SQ, or ProRes Proxy or LT when the list has it: whether the free edition on Linux offers ProRes for encoding is not confirmed here, only that the Studio edition does), then run `from-resolve FILE` (ffmpeg on the card) to make the H.265 or H.264 + AAC file that goes out, and delete the intermediate. An H.264 or H.265 export straight from the free edition on Linux is not available.

**Sharing a project between two Resolve installations (a recommendation, not built).** Resolve moves a project as a `.drp` archive (Project Manager, right click, Export Project; Import on the other side): that is the unit to hand over, and it carries the timeline, not the media. A project made in the free edition opens in Studio (the paid one adds features, it does not remove any); one made in Studio opens in the free edition but loses what only Studio has. The media must be reachable at the *same path* on both sides or be relinked. Because places are isolated by design, sharing is an explicit, narrow exchange: a folder mounted read-write in exactly the two places of a pair at the same path (for example `/exchange`), created and removed by the operator, holding the `.drp` and the DNxHR intermediates made by `to-resolve`. The paid copy would then be opened on the host with the USB key and reviewed there, and a third person takes their own copy of the same `.drp`. Resolve's database-based collaboration (a shared PostgreSQL project server) is a Studio feature and out of this setup.

**Proxy first, final pass on the paid copy (the intended flow).** The person who works in the free edition never touches the heavy originals: the proxies are made at the start (`to-resolve --quality lb FOLDER`, 41 GB per hour of 1080p60 against 198 for HQ, or ProRes Proxy at 20 GB if the free edition's Deliver page offers it), they edit and cut on those, and what travels is only the project (`.drp`) plus, if wanted, a rough export. The final stage (grade, effects, the render of the delivery file) is done on the paid copy, which relinks the project to the original media (Studio decodes H.264 and H.265) and renders from there. Keep the file names: `to-resolve` on a *folder* keeps each file's name and tree (only the extension becomes `.mov`), which is what relinking by name needs; on a single file it adds `-resolve`. Not verified: how Resolve's Relink Clips treats a changed extension, and Resolve's own proxy mode (Playback, Proxy Mode) in the free edition; both are worth one test before relying on this.

**Known problems and limits.**
- *Mouse in first-person games.* The pointer moves wrongly in a game that captures the mouse (reported while playing the Quake demo through the browser), the same symptom as Moonlight in desktop mode: the browser sends absolute positions and the game wants relative motion. Not fixed here; the places to look are Selkies' pointer-lock setting in its side panel and the game's own grab options (`in_nograb`, `in_mouse` in ioquake3). Untested.
- *Things installed by hand are lost on recreate:* VLC and htop are in the image now, but `ioquake3` and the Quake demo data (installed with `apt-get install ioquake3` and `game-data-packager quake3 --demo`, run with `ioquake3 +set com_basegame demoq3`) are not, on purpose.
- *Brave decodes video on the CPU* in a place (about 27 % of a core per stream); acceleration on the card was not tried.
- *Steam:* a `steam` command in each place installs the client into that person's folder the first time; the login and the game download are theirs and were not tried.
- *Resolve's import dialog and Media Storage* were checked only by the operator (a converted folder showed up); the free edition has no scripting, so none of it is automated.
- *AV1* is listed by the vendor for decode on any edition and was not tested; `to-resolve` re-encodes it.

**Where it can grow (not decided).** The way in from the internet below; dynamic game ports; an exchange folder per pair; a busy alert when someone opens a place while the owner plays on the host's own desktop (the card is shared); per-person disk quotas for the DNxHR intermediates; a model of what a modern game costs once one has been logged.

## Layout and rules
- `PLACES_ROOT/NAME/desktop` is the person's home (`/config` in the container); `input` and `output` are for files in and out; `.desktop.env` has the web login (0600); `.ports` has the pair of ports.
- Ports: `3010/3011` for the second place, then `3020/3021` and so on (`3000/3001` are the first one's). They are bound to **one private LAN address**, never to every interface: `place.py` refuses a public address and `0.0.0.0`.
- `restart=no`, 1 GB `/dev/shm` (browsers need it), `no-new-privileges`. A place starts stopped; the bot starts it when the person asks, through the same permission rule as the other on-demand containers.
- Everything in the person's folder is theirs: it is not read for reviews or backups without their word, and `rm` never deletes it.

## Network, addresses and limits (what a place can reach)
- **Own network per place.** `place.py` puts every place in its own docker network, `place-NAME-net`, a /24 of `172.30.0.0/16` taken from its port pair (3000 -> `172.30.0.0/24`, 3010 -> `172.30.1.0/24`, ...), with container-to-container traffic off. Never the shared default bridge, where two places and every other container could see each other.
- **Own LAN address per place.** Each place is published on its own address of the host's LAN interface (`--bind ADDRESS`; `PLACE_IPS` in `/etc/default/bridgeai-places`), so a person's desktop is `https://ADDRESS:3001` and the two places can be told apart in the router and in the logs. `places-net.sh up` adds the addresses (idempotent, announced on the LAN, on the interface that carries the default route: a NIC can be renumbered by the kernel) and `bridgeai-places-net.service` does it at boot. Reserve those addresses in the router so DHCP does not hand them to another device. Moonlight is unaffected: it goes to the host's own address, where Sunshine runs.
- **A place reaches the internet and nothing else.** `places-net.sh` loads the nft table `bridgeai_places` in the forward path (priority -5, ahead of docker's chain): traffic from the pool towards any private, link-local or carrier-grade range is dropped (no router, no other place, no other container, no other PC), except answers to connections the LAN opened to the published port. The host's own input chain (policy drop) already refuses what a container sends to the host itself, so the GPU gate and Sunshine are out of reach too. Audit it from inside: `curl` to the router, to the host's gate port and to the other place must fail; `curl` to a public site and DNS must work.
- **A LAN game between two places (proof of concept, measured).** Two people playing each other need the one narrow exception to the rule above: `PLACE_GAME_UDP=(PORT)` in `/etc/default/bridgeai-places` lets a place reach another place on that UDP port and nothing else, and the place that hosts publishes the port on its own LAN address (`place.py create|recreate NAME --udp PORT`, saved in `.settings.json`, kept by `recreate`, `--no-udp` clears it). The other connects to that address, not to the container's: `ioquake3 +connect HOST_PLACE_ADDRESS:27960` from the other place. Tested with the Quake III demo (the id Software demo from the vendor's mirror through Debian's `game-data-packager quake3 --demo`, run with `ioquake3 +set com_basegame demoq3`): one place as a listen server, the other joined and entered the game; both rendered on the card's own OpenGL (the log says `NVIDIA GeForce RTX 3060 Ti`), the two desktops together used 13 to 15 % of the GPU (the NVENC encoders, 12 to 14 %), 1.3 GB of VRAM, about 22 to 25 % of a core each and 0.5 GB of RAM each; the streams to the browsers ran at 0.5 and 1.0 Mbit/s. The same address also lets any PC on the LAN join that server. Static for now: one port list for the whole host. A game that needs other ports, or a port that is open only while a game runs, is the dynamic version (design below, not built).

- **Limits.** `--memory` and `--memory-swap` 9g, `--cpus` 5, `--pids-limit` 4096 (`PLACE_MEM`, `PLACE_CPUS`, `PLACE_PIDS`), so one person's session cannot starve the host desktop or the other place. What cannot be split is the card: VRAM, NVENC and power are shared by all containers and the host's own desktop (measured: 12 parallel NVENC sessions work, 8 GB of VRAM is the real ceiling). The gate's lease rules are the place to arbitrate that; there is no per-container GPU quota.
- **Software.** Inside the desktop there is no `sudo` that works (`no-new-privileges`): nothing can be installed or changed from the session. What a person needs is added to the image (`Dockerfile.place`: Brave, Telegram, ffmpeg, VLC, htop) or, for a one-off, installed as root from the host with `docker exec -u root` (lost when the container is recreated).

## Resolve, the free edition (a second layer)
Resolve is not in the base image: the vendor's installer is a download behind a registration form, so the operator downloads it (it cannot be fetched on anybody's behalf), and the **Studio** edition cannot be used here at all: its licence is a USB key tied to the host that has it. `build-resolve.sh DIR` takes the folder with the free `DaVinci_Resolve_<version>_Linux.zip` and `makeresolvedeb_*_multi.sh` (the package maker used on the host install), makes the `.deb` files from the vendor's file (nothing is redistributed, the folder is not in the repository), and builds `bridgeai-place-resolve` on top of `bridgeai-place` with `Dockerfile.resolve` (Qt's xcb plugin, ALSA's configuration, the OpenCL loader). It refuses a Studio file. Then `place.py create NAME --image bridgeai-place-resolve:latest --gpu` gives the place the card through the NVIDIA runtime; GPU work still goes through the GPU gate's rules (VRAM lease, concurrency, power).

What the free edition does and does not read on Linux (Blackmagic's own Linux codec table, confirmed on the host install; the operator tried an H.264 file in a place and it did not open, which is what the table predicts): **no AAC audio in any edition** (the sound of nearly every phone or game recording shows as offline), **no H.264/H.265 decoding without the Studio edition and its NVIDIA path** (there is no software fallback), and variable frame rate and interlaced footage need fixing first. What it does read is DNxHR/DNxHD and ProRes with PCM sound. So the helpers in `bin/` (tested with real ffmpeg clips, mounted read-only from this folder so a fix reaches every place at its next start without rebuilding the image) are not optional: `to-resolve [options] FILE|FOLDER [OUT]` (a Python tool, stdlib only, tested with real ffmpeg clips) looks at each file with ffprobe and decides, and says on stderr why. The video is copied untouched only when it is DNxHR/DNxHD or ProRes, at a constant frame rate and progressive; anything else, H.264 and H.265 included, becomes DNxHR at a constant standard frame rate (the nearest one when the source varies, or `--framerate`) and is deinterlaced (yadif) when interlaced; the sound becomes 24-bit PCM (PCM already there is copied; every audio track is kept). `--edition studio` leaves h264/hevc/av1 alone for a host with Studio and an NVIDIA card. `--quality lb|sq|hq|hqx|444` picks the DNxHR tier: **measured on a 10 s 1080p60 clip, `lb` 114 MB (about 41 GB per hour), `sq` 365 MB (131 GB/h), `hq` 551 MB (198 GB/h)**, so the default `hq` is generous: `lb` or `sq` is enough for a blog cut, `hqx` and `444` are 10-bit. On a folder it mirrors the tree into `FOLDER-resolve` next to it (`to-resolve ~/Videos` writes `~/Videos-resolve`, in the person's home; the tool prints the full path, each file's size and where to import from when it ends), skips what is already converted (resume, `--overwrite` to redo), runs `--workers` files at a time (2 by default), never walks into its own output, and ignores what is not video; `--dry-run` only reports. The source is decoded on the NVIDIA card when ffmpeg can (`--gpu-decode auto|on|off`; a file the card cannot decode is retried on the CPU), measured in a place at four times real time for 1080p60, while the DNxHR encoding itself always runs on the CPU. Output is written to a `.part.mov` and renamed when whole, so a stopped run leaves nothing half-made that looks finished. `from-resolve [--max-mb N] [--gpu] FILE` turns an export back into an H.264 (or, with the card, H.265) + AAC mp4 with `faststart`, sized to fit N megabytes (1900 by default, under the 2000 MB of the local Bot API). The ideas of the frame-rate, interlace and audio rules come from the community's `davincirecode10.sh` thread on the vendor's forum. Media and render folders must sit inside Resolve's Media Storage (the person's home), or a modal dialog blocks everything.

## Opening and closing from the bot (`gateway escritorio`)
The person's stack opens, closes and watches only its own place, through the GPU gate on the host (`/place/*`), with a token that belongs to that place.
- **Token per place.** `place.py gate-token NAME` writes `NAME/.gate.token` (0600, the stack gets this one, through `ops/gateways_sync.py`: the stack's `"escritorio": {"host", "token"}` entry) and `NAME/.gate.hash` (0644, only the sha256: the gate reads this). `create` makes both. The token is neither the gate's token nor the host's (games, power): `/place/*` refuses those, and `/host/*` refuses a place token. A stack can therefore never open another person's desktop. `--rotate` replaces it and the old one stops at once.
- **Verbs.** `gateway escritorio abrir|cerrar|seguir|estado` (also `open|close|keep|status`). `abrir` starts the container and says the web addresses (http on the first port, https on the second) and the 30-minute rule; `seguir` gives a new full turn; `cerrar` stops it. Files are never touched by any of them.
- **Idle close.** The gate checks every minute. A place counts as in use when somebody touched the screen in the last 90 seconds (the X server's idle time, asked inside the container with a few lines of ctypes sent over `docker exec`, nothing installed) or when the container works at 80 % CPU or more (a render with nobody at the keyboard). An open tab nobody touches is not use. After 20 minutes of no use the person is warned; after 30 the container is stopped (`docker stop`, 20 s grace). `PLACE_IDLE_S`, `PLACE_WARN_S`, `PLACE_BUSY_CPU`, `PLACE_ACTIVE_S` and `PLACE_TICK_S` tune it. A place started by hand with `place.py start` gets its clock when the gate first sees it, so it is not closed on the spot.
- **The warning reaches the person** through `jobwatch` (the no-LLM job that runs every 5 minutes): `abrir` leaves an entry `{"watch": "escritorio"}` in `/workdir/jobs`, and each run asks `gateway escritorio aviso` (a fixed command; nothing from the file reaches it) for the warning (10 minutes before the close, so at least 5 minutes of notice) and for the closing notice, once each. The entry ends itself when the place is closed.
- **Shared card.** Two places and the host's own desktop share one GPU (VRAM, NVENC, power). `estado` and `abrir` say only that another place is open (a count), never whose; a real "busy" alert is future work.
- **Recreating.** `place.py recreate NAME [--image IMG] [--gpu|--no-gpu]` removes the container (refused while it runs) and makes it again from the saved settings (`.settings.json`): same folders, ports and login. This is how a place changes image.

## Steam
The person's own account, signed in inside their place, never the operator's. Steam's terms are for a personal account and no sharing: nothing in this setup stores or reuses a login for anyone else. The `steam` command of each place installs the client into that person's folder the first time; the login and the downloads were not tried.

## Files in and out through Telegram (built, not yet tried on a real desktop)
The person sends and receives everything through the bot and works in Resolve on the desktop. Only the place's `input` and `output` folders are reachable; `desktop` (the person's home) never is.
- **In:** `gateway escritorio subir PATH [crudo|lb|sq|hq]`. The file must be one the person sent (inside the stack's work dir, nothing hidden on the way). It is streamed to the gate's `POST /place/input` (up to 1.9 GB, a free name when taken, written as a hidden `.part` and renamed when whole, refused when it would leave less than 8 GB free). A video is then converted inside the place with `to-resolve` (DNxHR + PCM, default `hq`) into `input/resolve/NAME.mov`; that needs the place open, and says so when it is not (`escritorio convertir NAME` later). `crudo` skips the conversion.
- **Work:** the person edits on the desktop and exports into `/output`.
- **Out:** `gateway escritorio bajar [NAME] [crudo]` (newest export without a name). A video that Telegram cannot play (`.mov`, `.mxf`, `.mkv`, `.avi` ...) or over 1.9 GB is first made into an mp4 that fits with `from-resolve` (inside the place, in the background, into `output/telegram/NAME.mp4`; the bot is told to ask again later); an mp4 that fits is downloaded as it is, into the stack's `/workdir/lugar` and sent as a `MEDIA:` line. A file over the limit that is not a video stays where it is. `gateway escritorio archivos` lists both folders and counts what is still being made; `gateway escritorio borrar NAME` deletes an export **only after the person says it arrived**.
- **Gate endpoints** (the place's own token only): `GET /place/files`, `GET /place/file?name=`, `POST /place/input?name=`, `POST /place/convert`, `/place/shrink`, `/place/delete`.
- **Links are never followed.** The person's own container writes into `output` and can plant a symbolic link there; the gate runs as the host user and could be made to read the host's files through it (its own token file, for one). So every open walks the path one directory at a time with `O_NOFOLLOW`, serves only regular files, lists no links, and a name is one safe component per level (no `..`, no leading dot or dash, at most three levels). Both ends are tested with planted links to a host file, a folder and the person's home.
- **Folder ownership.** `place.py create` now gives `input` and `output` to uid 1000 (the container's user and the gate's); a place created before this needs `sudo chown 1000:1000 NAME/input NAME/output` once, or Resolve cannot write its exports there.
- **Not done:** a video that does not fit even after shrinking (a very long export at 1.9 GB is about 3 Mbit/s for 80 minutes; `from-resolve` refuses below what is watchable), other big files in pieces, and a per-person disk quota. Whether Telegram's own player takes the shrunk mp4 and how `MEDIA:` treats an arbitrary document type (a `.drp`) were not tried.

## Ports
Only the web door of the desktop is published, and only on the LAN: `3011/tcp` (HTTPS) and `3010/tcp` (HTTP, redirects) for the second place, then `3021` and `3020`, and so on. Selkies streams over a WebSocket on the same port, so no UDP range is needed (confirmed: the streams work with only the two TCP ports published). The plain-HTTP port answers the same login as the HTTPS one (it does not redirect), and a browser that refuses the self-signed certificate can use it on the LAN. Resolve's own scripting listener (TCP 15000) stays inside the container and is never published. What "giving her the ports" means is the on-demand door below: the one TCP port of her place, opened for a limited time at her request and closed otherwise.

## The way in from the internet (design only, not built)
Today a place answers only on the LAN. Anyone outside gets in only through a door that is **closed by default and opened on request**, for a limited time, by the person asking the bot. Two ways, the first preferred:
1. **A tunnel that exists only while open** (outbound connection from the host to an edge service with its own login in front), started on the person's request and stopped after a time. No inbound port is ever opened, so the host firewall can stay as it is.
2. **A firewall window plus a port forward on the router**: a set in the host's own firewall table with a timeout per source address, and a forward made on request and removed at the end. More moving parts (the router, the person's changing address), and Selkies' WebRTC wants UDP.
Either way the request, the time left and the close are visible to the person (`/abrir`, `/cerrar`) and to the operator, and the window ends by itself.

## Dynamic game ports (design, not built)
Docker fixes the published ports when a container is created, so "open the port when a game starts" cannot be done by publishing. The dynamic form lives in the host firewall instead: the gate gets `/place/ports` (the place's own token; `open` with protocol, port and a lifetime, `close`, `list`) and keeps a small nft table of its own with two things per open port: a DNAT from the place's LAN address and port to the container, and the permission for the other places to reach that container port. Every entry carries an expiry that the gate's one-minute clock enforces, the ports a person may ask for are capped in number and range, and an entry is removed when the place closes. Different games need different ports (Quake III 27960/udp, Source games 27015 tcp and udp, Minecraft 25565/tcp): a small table of known games maps a name to its ports, so the person says "open the Quake port" and nothing free-form reaches the firewall. Scale: each place needs its own LAN address (aliases on the interface cost nothing, but each should be reserved in the router) and one entry per open port; the limit is the card (8 GB of VRAM: a Quake-class game takes about 0.3 GB, a modern one 3 to 6 GB, so two modern games at once is the ceiling), not the network (a stream is 0.5 to 1 Mbit/s here) nor the encoder (12 NVENC sessions tested).
